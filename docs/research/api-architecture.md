# Simple TypeScript + PostgreSQL API Architecture Research

_Research for [#3](https://github.com/andikon/HomeOrg/issues/3), part of the [#1](https://github.com/andikon/HomeOrg/issues/1) Wayfinder map._

## Question

For a small, self-hosted, public-HTTPS "Household Organization" REST/JSON API (single household, few members, low traffic — simplicity and long-term solo/small-team maintainability matter far more than raw performance or extensibility), what is a cohesive, simple, currently-maintained (2025/2026-era) TypeScript + PostgreSQL architecture? Fixed constraints: TypeScript, PostgreSQL, Docker Compose, host Nginx reverse proxy terminating public HTTPS, REST/JSON API with a documented OpenAPI contract. The research compares, using only official/primary sources (docs, GitHub repos, npm registry metadata), viable options for: (1) HTTP framework, (2) PostgreSQL data-access/query layer, (3) migrations, (4) validation + OpenAPI generation, (5) environment configuration, and (6) testing baseline — then recommends one cohesive combination.

## Comparison: HTTP framework

| Framework | Current version (npm `latest`, verified via registry) | Node.js support (own docs) | Async / error-handling model | TypeScript story |
|---|---|---|---|---|
| **Express** | `5.2.1` (`engines.node: ">= 18"`) — verified via `registry.npmjs.org/express/latest` | Requires **Node.js 18+** per its own 5.x API docs | Express 5 natively awaits route handlers: "Route handlers and middleware that return a Promise call `next(value)` automatically when they reject or throw an error, and `async` functions always return a Promise, so their errors reach Express with no extra work" — [expressjs.com/en/guide/error-handling](https://expressjs.com/en/guide/error-handling/). This is a **behavior change from Express 4**, documented in the migration guide ([expressjs.com/en/guide/migrating-5](https://expressjs.com/en/guide/migrating-5/)), which also lists breaking changes (removed `app.del()`, pluralized `req.acceptsCharset()` → `acceptsCharsets()`, `res.json(obj, status)` removed, etc.) and provides official codemods. | Express itself ships no first-party generic-typed request/response system; official examples in the error-handling guide show plain `import { type Request, type Response } from 'express'` typing, i.e. typings are structural, not schema-derived. |
| **Fastify** | `5.12.5` current stable (npm registry `latest`); v6 is in `alpha` on the `main` branch (`fastify@6.0.0-alpha.4` per `raw.githubusercontent.com/fastify/fastify/main/package.json`) — verified via `registry.npmjs.org/fastify/latest` | Plugin/version support matrix maps Fastify `^5.x` ⇄ plugin versions ≥9.x for `@fastify/swagger` — [github.com/fastify/fastify-swagger](https://github.com/fastify/fastify-swagger) (see LTS table) | `async/await` supported "out-of-the-box": `fastify.get('/', async (request, reply) => { return { hello: 'world' } })` — [fastify.dev/docs/latest/Guides/Getting-Started](https://fastify.dev/docs/latest/Guides/Getting-Started/) | Fastify has invested specifically in TS typings since "version 3", introducing "generic constraining and defaulting" and typed schema for body/querystring/params/headers/reply — [fastify.dev/docs/latest/Reference/TypeScript](https://fastify.dev/docs/latest/Reference/TypeScript/). First-class **schema-based validation/serialization**: "Fastify uses a schema-based approach... We recommend using JSON Schema to validate routes and serialize outputs. Fastify compiles the schema into a highly performant function" using **Ajv v8** for validation — [fastify.dev/docs/latest/Reference/Validation-and-Serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/). |
| **Hono** | `4.13.9` (`engines.node: ">=16.9.0"` per npm registry metadata) — verified via `registry.npmjs.org/hono/latest` | Official Node.js guide states it "works on Node.js versions greater than 18.x," listing minimums per major (18.14.1+, 19.7.0+, 20.0.0+) via the `@hono/node-server` adapter — [hono.dev/docs/getting-started/nodejs](https://hono.dev/docs/getting-started/nodejs). Note: **Hono was not designed for Node.js first** — it targets Web Standards runtimes (Workers, Deno, Bun, etc.) and needs an adapter package to run on Node. | Handlers are plain async functions returning Web-standard `Response`-like values; framework is built "on Web Standards" — [hono.dev/docs](https://hono.dev/docs). | Docs advertise "First-class TypeScript support," "Delightful DX," and a `hono/tiny` preset "under 14kB" vs. "the size of Express is 572KB" — [hono.dev/docs](https://hono.dev/docs) and [github.com/honojs/hono](https://github.com/honojs/hono). Hono has zero dependencies by design. |

**Takeaway:** All three currently support modern async/await natively. Express 5 finally closed its historic async-error gap (a Node 18+, actively maintained major). Fastify is the only one of the three with a first-party, docs-backed schema validation/serialization pipeline (Ajv-based) and an ecosystem plugin (`@fastify/swagger`) purpose-built for OpenAPI generation tied to those same schemas. Hono is optimized for edge/multi-runtime deployment and minimal bundle size; on Node.js it requires the `@hono/node-server` adapter, which is an extra moving part for a single self-hosted Node process that doesn't need multi-runtime portability.

## Comparison: Data access & migrations

| Layer | Own-docs claims | Node/PG compatibility | Migration story |
|---|---|---|---|
| **`pg` (node-postgres)** | Raw driver: "a collection of node.js modules for interfacing with your PostgreSQL database," with "support for callbacks, promises, async/await, connection pooling, prepared statements, cursors, streaming results" — [node-postgres.com](https://node-postgres.com/) | "supports every version of the PostgreSQL database from 8.x to the most recent version," and "all current and LTS versions of node as well as bun, deno, and cloudflare workers"; explicitly compatible with "node 18.x, 20.x, 22.x, and 24.x" — [node-postgres.com](https://node-postgres.com/) | No native migration tooling; you write raw SQL yourself or pair with a standalone tool (e.g., `node-pg-migrate`). |
| **Drizzle ORM** | Self-described as a "headless TypeScript ORM," explicitly **not** an ORM in the Django/Spring sense — "you have to build projects around them and not with them... Drizzle lets you build your project the way you want" — [orm.drizzle.team/docs/overview](https://orm.drizzle.team/docs/overview). Claims "the only ORM with both relational and SQL-like query APIs," "Drizzle always outputs exactly 1 SQL query," and "Drizzle has exactly 0 dependencies" — same page. Current version `drizzle-orm@0.45.3` per `registry.npmjs.org/drizzle-orm/latest`. | Has "native support for PostgreSQL connections with the `node-postgres` and `postgres.js` drivers" — you initialize with `drizzle(process.env.DATABASE_URL)` from `drizzle-orm/node-postgres` — [orm.drizzle.team/docs/get-started-postgresql](https://orm.drizzle.team/docs/get-started-postgresql). Drizzle sits directly on top of `pg`, i.e. it's additive to node-postgres, not a replacement runtime. | **drizzle-kit** is the official CLI: `drizzle-kit generate \| migrate \| push \| pull \| check \| up \| studio \| export`, configured via `drizzle.config.ts` (`dialect: "postgresql"`, `schema`, `out`) — [orm.drizzle.team/docs/kit-overview](https://orm.drizzle.team/docs/kit-overview). Docs explicitly describe both a **"codebase first"** flow (`drizzle-kit generate` produces a timestamped folder with `migration.sql` + `snapshot.json`, then `drizzle-kit migrate` applies unapplied migrations by tracking migration history in the DB) and a **"database first"** flow (`drizzle-kit pull` introspects the DB into TS schema) — [orm.drizzle.team/docs/migrations](https://orm.drizzle.team/docs/migrations). |
| **Kysely** | "a type-safe and autocompletion-friendly TypeScript SQL query builder... mainly developed for node.js" — [kysely.dev/docs/intro](https://kysely.dev/docs/intro). Requires you to hand-write (or generate) a `Database` interface describing every table; "Kysely only deals with types in the TypeScript level. The runtime JavaScript types are decided by the underlying third-party driver such as `pg`" — [kysely.dev/docs/getting-started](https://kysely.dev/docs/getting-started?dialect=pg). Minimum TypeScript **5.4**, `strict` mode required. | Built-in PostgreSQL dialect "uses the 'pg' driver library under the hood" — same page. | No first-party migration generator from schema; Kysely ships a `Migrator` API to run up/down migration files you write by hand — schema changes and migrations are your responsibility, distinct from Drizzle's schema-driven `drizzle-kit generate`. |
| **Prisma** | "Prisma ORM is an open-source next-generation ORM," consisting of **Prisma Client** (auto-generated type-safe query builder), **Prisma Migrate** (migration system), and **Prisma Studio** (GUI, "the only part... not open source") — [prisma.io/docs/orm/overview/introduction/what-is-prisma](https://www.prisma.io/docs/orm/v6/overview/introduction/what-is-prisma). Uses its own declarative schema language (`schema.prisma`) plus a separate `prisma.config.ts` for connection/migration path config, and requires a code-generation step to produce Prisma Client before use. | Postgres supported as a first-party `datasource` provider. | **Prisma Migrate** is Prisma's own migration system (declarative schema → generated SQL migrations), fully integrated with the `prisma.config.ts` `migrations.path`/`seed` settings shown in the official example — same page. |
| **node-pg-migrate** (standalone) | "Node.js database migration management built exclusively for postgres." Requires **Node.js 22+** and **PostgreSQL 14+** per its own README (lower may work, unsupported) — [github.com/salsita/node-pg-migrate](https://github.com/salsita/node-pg-migrate). Migration files export `up`/`down` functions receiving a `pgm` builder object (e.g. `pgm.createTable(...)`), run via `node-pg-migrate up`, using a `DATABASE_URL` env var — same README. Rationale given directly in the README: "By writing this migration tool specifically for postgres instead of accommodating many databases, we can actually provide a full featured tool that is much simpler to use and maintain," and "a migration tool should really just be a fancy wrapper that generates SQL." | Pairs with `pg` as a peer dependency. | Up/down semantics are explicit per-file JS/TS functions; the tool "automatically infer[s] down migrations (sometimes)" from the recorded up operations. |

**Takeaway:** `pg` alone gives zero abstraction/typing and no migration story — appropriate only if paired with a separate migration tool and hand-written SQL/types. Prisma is powerful but layers on a non-SQL schema DSL, a required code-gen step, and its own CLI/config surface — heavier than needed for a single-household app. Kysely gives excellent SQL-shaped type safety but requires you to hand-maintain (or generate) the `Database` interface and doesn't provide first-party schema-diff migration generation. **Drizzle** is the best fit for "simple": it is SQL-shaped ("if you know SQL, you know Drizzle"), has zero runtime dependencies, sits directly on the `pg` driver, and ships an official CLI (`drizzle-kit`) that both defines the TypeScript schema (source of truth) and generates/applies plain `.sql` migration files with a migration-history table in Postgres — a self-contained migrations story without introducing a second standalone tool.

## Comparison: Validation & OpenAPI

| Approach | Own-docs claims | Request validation | Response validation | OpenAPI generation |
|---|---|---|---|---|
| **Zod** (`zod@4.6.5` per npm registry) | "TypeScript-first schema declaration and validation library with static type inference" (npm package description, `registry.npmjs.org/zod/latest`); homepage banner confirms current major is "Zod 4.6" — [zod.dev](https://zod.dev/) | Yes — schemas double as request parsers. | Yes, when paired with a serializer (see below). | Not built-in to core Zod; requires a companion library. |
| **`zod-openapi`** | "A TypeScript library which uses Zod schemas to generate OpenAPI v3.x documentation," leveraging Zod's **native `.meta()` method** — "no monkey patching or additional setup is required" — [github.com/samchungy/zod-openapi](https://github.com/samchungy/zod-openapi). Example shows `createDocument({ openapi: '3.1.0', ... })` consuming the same `z.object(...)` schemas used for `requestParams`/`requestBody`/`responses`, i.e. one schema drives both validation and docs. | Via the same Zod schemas used at runtime. | Via the same schemas (response schemas included in `responses` block). | Generates full OpenAPI 3.x documents directly from Zod schemas. |
| **`@asteasolutions/zod-to-openapi`** | "A library that uses zod schemas to generate an Open API Swagger documentation," motivated explicitly to avoid "duplication to also support a separate OpenAPI definition that must be kept in sync" — [github.com/asteasolutions/zod-to-openapi](https://github.com/asteasolutions/zod-to-openapi). Uses a `registry.registerPath({...})` API with `request.params`/`responses` built from Zod schemas; **v8+ can read Zod's native `.meta()`** instead of its own `.openapi()` method when using Zod v4 — same README. Current stable targets **Zod v4.2+**; v3 support frozen at `7.3.4`. | Yes. | Yes. | Yes, produces Swagger/OpenAPI YAML/JSON. |
| **TypeBox** | "a runtime type system that creates in-memory JSON Schema objects that infer as TypeScript types... designed to allow JSON Schema to compose similar to how types compose within TypeScript's type system" — [github.com/sinclairzx81/typebox](https://github.com/sinclairzx81/typebox). Schemas (`Type.Object({...})`) are plain JSON Schema at runtime, so they can be handed directly to any JSON-Schema validator (e.g. Ajv, which is what Fastify already uses) and directly reused as OpenAPI schema fragments (OpenAPI 3 schemas are JSON-Schema-based). | Yes, via JSON Schema. | Yes, same schema reused for response. | JSON Schema output is compatible with OpenAPI's schema objects, but TypeBox itself does not ship an OpenAPI-document generator — that's left to the consuming framework's own tooling (e.g., `@fastify/swagger`, which builds Swagger/OpenAPI docs "automatically generated from your route schemas"). |
| **`@fastify/swagger`** (framework-native OpenAPI) | "A Fastify plugin for serving Swagger (OpenAPI v2) or OpenAPI v3 schemas, which are automatically generated from your route schemas" — [github.com/fastify/fastify-swagger](https://github.com/fastify/fastify-swagger). Version compatibility is explicitly pinned to Fastify majors: plugin `>=9.x` ⇄ Fastify `^5.x` — same README. Must be registered **before routes** to be picked up. | Delegates to Fastify's own route `schema.body/querystring/params` validation (Ajv). | Delegates to Fastify's own route `schema.response`. | Builds the OpenAPI document from the same `schema` object attached to each Fastify route — i.e., one schema source drives runtime validation, serialization, and docs simultaneously. |
| **`fastify-type-provider-zod`** (bridges Zod ⇄ Fastify ⇄ `@fastify/swagger`) | Lets Fastify routes declare `schema: { querystring: z.object({...}), response: { 200: z.string() } }` directly; you register `validatorCompiler`/`serializerCompiler` from the package so Fastify validates/serializes using Zod instead of raw JSON Schema, and pass `transform: jsonSchemaTransform` into `@fastify/swagger` registration so the **same Zod schemas** also produce the OpenAPI document — [github.com/turkerdev/fastify-type-provider-zod](https://github.com/turkerdev/fastify-type-provider-zod). Version table shows current major (`>=7.x`) requires **Zod v4.2+** and uses Zod's `.encode()/.decode()` APIs, meaning "Fastify serializers always expect the post-transformation output type" of Zod schemas. Also documents error handling: `hasZodFastifySchemaValidationErrors(err)` for request-side errors vs `isResponseSerializationError(err)` for response-side errors — same README, meaning **both request and response validation** are explicitly first-class and distinguishable. | Yes (Zod). | Yes (Zod), explicitly distinguished from request errors in the error-handling example. | Yes, via `@fastify/swagger`'s `transform: jsonSchemaTransform` option, driven by the same Zod schemas. |

**Takeaway:** For a Fastify-based API, the officially-documented, single-source-of-truth path is: **Zod schemas → `fastify-type-provider-zod` (validator + serializer compilers) → `@fastify/swagger` (OpenAPI document) → `@fastify/swagger-ui`** (not separately verified above, but referenced in the `fastify-type-provider-zod` example alongside `@fastify/swagger`). This avoids maintaining a parallel OpenAPI spec or duplicate JSON-Schema/TypeBox definitions, and both request and response validation are explicitly supported and distinguishable in error handling per the package's own docs.

## Configuration

- **dotenv** ("Dotenv is a zero-dependency module that loads environment variables from a `.env` file into `process.env`," explicitly based on "The Twelve-Factor App methodology") loads config as early as possible via `import 'dotenv/config'` (ESM) or `require('dotenv').config()` (CJS) — [github.com/motdotla/dotenv](https://github.com/motdotla/dotenv). Its own docs also document a companion CLI (`dotenv-cli`) and multiline/quoted-value/comment parsing rules, useful for `.env` files consumed identically by local dev and Docker.
- **Schema-validating the loaded env** with the *same validation library* chosen for request/response validation (Zod) keeps one dependency doing double duty: parse `process.env` through a `z.object({...})` schema at startup (e.g., `DATABASE_URL: z.string().url()`, `PORT: z.coerce.number()`) so misconfiguration fails fast at boot rather than at first request. (This composition pattern is an application of Zod's own documented `z.object().parse()` API — [zod.dev](https://zod.dev/) — no framework-specific env-validation package is required.)
- **Docker Compose's own docs** describe two first-party mechanisms for injecting configuration into containers:
  - The `environment` attribute (list or mapping syntax) directly in `compose.yaml`, which also supports shell pass-through (`- DEBUG`) and interpolation (`- DEBUG=${DEBUG}`), the latter warning if the variable is unset — [docs.docker.com/compose/how-tos/environment-variables/set-environment-variables](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/).
  - The `env_file` attribute, which loads variables from one or more `.env`-format files relative to the `compose.yaml` location; "If multiple files are specified, they are evaluated in order and can override values set in previous files," and (since Compose 2.24.0) individual files can be marked `required: false` — same page.
  - The same page explicitly warns: **"Don't use environment variables to pass sensitive information, such as passwords, in to your containers. Use secrets instead,"** pointing to Compose's separate secrets how-to (not independently verified in this pass, but directly linked from the environment-variables doc as the recommended mechanism for credentials).
- **Composition for this project:** a single Zod schema (`env.ts`) validates `process.env` once at process start (loaded via `dotenv/config` in local/dev, and via Compose `env_file:`/`environment:` in Docker), giving one consistent, typed config surface across `npm run dev` and the container — while secrets specifically should use Compose secrets rather than plain `environment:` per Docker's own guidance above.

## Testing baseline

| Runner | Own-docs claims | TS support | ESM support | Speed/positioning |
|---|---|---|---|---|
| **Vitest** (`vitest@5.0.2` per npm registry `latest`, `engines.node: "^22.12.0 \|\| ^24.0.0 \|\| >=26.0.0"`) | "Vitest was created to make testing just work for Vite apps... You can also use Vitest even if you are not using Vite. It is Jest-compatible and works for backend code too" — [vitest.dev](https://vitest.dev/) | Native, since it reuses Vite's TS transform pipeline; no separate ts-jest/babel config needed. | Native ESM by design (package is `"type": "module"`-first per docs). | Positioned as the Vite-native, Jest-API-compatible successor for backend and frontend alike. |
| **`node:test`** (Node.js built-in) | Official Node.js docs: "The `node:test` module facilitates the creation of JavaScript tests," supporting sync functions, `Promise`-returning async functions, and callback-style tests, with subtests via `t.test(...)` and a `--test-rerun-failures` state-file mode — [nodejs.org/api/test.html](https://nodejs.org/api/test.html) | No transform layer — requires running compiled JS or a loader (e.g. `--experimental-strip-types`/`tsx`) since `node:test` itself does not transpile TypeScript. | Runs on Node's native ESM loader directly (no bespoke ESM shims). | Zero extra dependency — ships with Node itself. |
| **Jest** | Own docs: ESM support is explicitly labeled **"experimental"** — "Jest ships with experimental support for ECMAScript Modules (ESM). The implementation may have bugs and lack features," requiring `node --experimental-vm-modules` and disabling/reconfiguring the `transform` option — [jestjs.io/docs/ecmascript-modules](https://jestjs.io/docs/ecmascript-modules). TypeScript support is via Babel's `@babel/preset-typescript` (type-stripping only, no type-checking) or `ts-jest`, per the "Using TypeScript" section of the getting-started guide — [jestjs.io/docs/getting-started#using-typescript](https://jestjs.io/docs/getting-started#using-typescript). Jest's own docs note "Jest is not supported by Vite due to incompatibilities with the Vite plugin system... One alternative is Vitest which has an API that is compatible with Jest" — same page. | via Babel/ts-jest | experimental | — |

**Takeaway:** Vitest has the least configuration overhead for a modern TS/ESM Node project (native TS + ESM, Jest-compatible API for familiarity) per its own docs. `node:test` is a legitimate zero-dependency alternative but needs an extra TS-stripping step and lacks Vitest's built-in mocking/coverage ergonomics. Jest itself flags its own ESM support as experimental and, per its own docs, effectively defers ESM+Vite-friendly use cases to Vitest.

**Integration testing against real Postgres:** Testcontainers-node is the primary-source-documented approach: `@testcontainers/postgresql`'s own docs show `await using container = await new PostgreSqlContainer(IMAGE).start()`, then connecting with the standard `pg` `Client` via `container.getHost()/getPort()/getDatabase()/getUsername()/getPassword()` or `container.getConnectionUri()` — [node.testcontainers.org/modules/postgresql](https://node.testcontainers.org/modules/postgresql/). The general Testcontainers-node docs describe it as "a library that supports tests, providing lightweight, throwaway instances of common databases... or anything else that can run in a Docker container" — [node.testcontainers.org](https://node.testcontainers.org/). Since Docker Compose is already a fixed project dependency, spinning up an ephemeral Postgres container per test run via Testcontainers (rather than mocking the DB) keeps integration tests honest against real Postgres semantics without hand-rolled Compose test profiles.

## Recommendation

**Decision gist:** Recommend Fastify + node-postgres/Drizzle ORM + drizzle-kit migrations + Zod/fastify-type-provider-zod + @fastify/swagger for OpenAPI + dotenv/Zod-validated env + Vitest/testcontainers-node for a simple self-hosted TS/Postgres household API.

For this single-household, low-traffic, solo/small-team-maintained API, the recommended cohesive stack is: **Fastify** (`fastify@5.x`, Node 18+ per its own docs) as the HTTP framework, chosen over Express 5 for its first-party schema-driven validation/serialization pipeline and over Hono for avoiding an unnecessary multi-runtime adapter layer on a plain self-hosted Node process; **Drizzle ORM** (`drizzle-orm` on top of the `pg`/`node-postgres` driver) as the data-access layer, chosen for its zero-dependency, SQL-shaped API and because it avoids Prisma's separate schema DSL/code-gen step and Kysely's hand-maintained `Database` interface; **drizzle-kit** (`generate` + `migrate`) as the migration tool, since it is Drizzle's own first-party CLI and keeps the TypeScript schema as the single source of truth for both the application and the migration `.sql` files, run inside the Docker Compose startup sequence (or a CI step) rather than adding a second standalone migration tool like `node-pg-migrate`; **Zod** schemas shared across the app, wired into Fastify via **`fastify-type-provider-zod`** (`setValidatorCompiler`/`setSerializerCompiler`) for both request *and* response validation, and fed into **`@fastify/swagger`** (`transform: jsonSchemaTransform`) plus `@fastify/swagger-ui` to auto-generate and serve the OpenAPI 3.x contract from those same schemas — a single source of truth instead of TypeBox+manual OpenAPI or a hand-maintained spec; **dotenv** to load `.env` files locally (with Docker Compose's own `environment:`/`env_file:` attributes doing the equivalent job in containers, and Compose secrets — not `environment:` — for actual credentials per Docker's own guidance) combined with a small Zod schema that parses and validates `process.env` once at boot; and **Vitest** as the test runner (native TS/ESM per its own docs, Jest-compatible API, faster setup than Jest's experimental-ESM path or `node:test`'s lack of built-in TS support) paired with **`@testcontainers/postgresql`** to spin up a real, throwaway Postgres container for integration tests rather than mocking the database. This combination keeps exactly one framework (Fastify), one schema library (Zod) serving three purposes (validation, serialization, OpenAPI), one migration tool (drizzle-kit) tied to one ORM, and one config-validation mechanism reused from the same schema library — deliberately avoiding microservices, caching layers, queues, or a heavier ORM/framework than a single-household deployment needs.

**Trade-offs called out:**
- Fastify's plugin/schema-based architecture has a steeper initial learning curve than Express's near-zero-config style, but pays off directly here because it is what makes the "one schema, three jobs" (validate/serialize/OpenAPI) pattern possible with `fastify-type-provider-zod` + `@fastify/swagger` — Express would need a separate OpenAPI generator (e.g. `zod-openapi`/`@asteasolutions/zod-to-openapi`) wired in manually with no framework-level request/response schema enforcement.
- Drizzle's "codebase first" migration flow (`drizzle-kit generate` + `migrate`) requires committing generated `.sql` files to version control and running `drizzle-kit migrate` as an explicit deploy/CI step; teams that want the ORM to auto-sync schema at runtime could use `drizzle-kit push` instead, but that is better suited to prototyping than a versioned production deployment.
- `fastify-type-provider-zod` v7+ pins to Zod's newer `.encode()/.decode()` semantics (Zod 4.2+), so response types are the Zod *output* type, not the input type — a detail to watch for schemas using `.transform()`.
- Testcontainers-node integration tests require Docker to be available wherever tests run (already true for this project's Compose-based deployment target, but note if CI runners lack Docker-in-Docker).
